\section{Komponen dan Tanggung Jawab}
Setiap service mengelola satu bagian dari alur data, sehingga perubahan dan gangguan dapat dibatasi pada bagian tersebut. Dua mock mewakili instansi sumber: BMKG menyediakan gempa dan warning, sedangkan PVMBG menyediakan laporan vulkanik. Keduanya bersifat pasif dan hanya mengirim data sebagai respons terhadap polling. Endpoint admin mendukung simulasi perubahan schema, delay, dan outage.

Aggregator menjadi penghubung antara kontrak sumber dan kontrak BNPB. Service ini memvalidasi payload, menghubungkan warning dengan gempa, lalu memetakan hasilnya ke HazardEvent. Aggregator juga mengelola Canonical Store dan menyediakan API internal agar service lain dapat meminta data tanpa bergantung pada struktur tabelnya.

Akses client ditangani oleh Client-Facing API dan Auth. Auth memeriksa identitas dan menerbitkan token dengan scope yang sesuai. Setelah itu, Client API memverifikasi token dan menyaring field yang boleh dibaca. Dengan demikian, pengambilan data dari sumber tetap terpisah dari aturan penyajiannya kepada client.

Untuk distribusi perubahan, NATS JetStream menyimpan event yang diterbitkan Aggregator. Dashboard Consumer mengolahnya menjadi state dashboard, sedangkan Notifier Consumer mencatat alert. Setiap consumer memiliki posisi baca dan database sendiri, sehingga berhentinya satu consumer tidak menghentikan consumer lain.

\section{Alasan Pembagian Service}
Pembagian service mengikuti perbedaan tanggung jawab, kebutuhan akses, dan kepemilikan data. Bagian yang mengelola data yang sama tetap digabung, sedangkan bagian yang perlu berubah atau pulih secara independen dipisahkan. Pertimbangan ini menghasilkan batas berikut.

Polling, mapping, query internal, dan relay ditempatkan dalam Aggregator karena semuanya menggunakan Canonical Store yang sama. Loop dan pool koneksi dipisahkan untuk mengisolasi pekerjaan di dalam service tersebut. Alternatifnya, ingest tiap instansi dapat menjadi service sendiri, tetapi perlu antarmuka serta koordinasi storage tambahan. Pilihan satu Aggregator lebih sederhana untuk M1, dengan konsekuensi semua pekerjaan ingest berhenti jika containernya mati.

Client API dipisahkan dari Aggregator agar perubahan hak akses dan format respons tidak mengharuskan rebuild jalur ingest. Auth menjadi service tersendiri untuk menjaga private key penandatanganan token, sementara API cukup memegang public key. Verifikasi JWT dilakukan secara lokal di API, sehingga request dengan token yang masih valid tetap dapat dilayani ketika Auth berhenti. Login dan refresh tetap membutuhkan Auth.

Dashboard dan Notifier dipisahkan karena masing-masing menghasilkan state aplikasi yang berbeda. Container, database, dan durable consumer tersendiri memungkinkan keduanya dipulihkan secara independen. Third Consumer digunakan untuk menguji penambahan aplikasi pembaca: consumer ini memakai binary Notifier, tetapi memiliki durable dan volume sendiri. Dengan kontrak event yang sama, producer tidak perlu diubah ketika pembaca baru ditambahkan.

\section{Protokol dan Alur Komunikasi}
Komunikasi sistem mengikuti dua alur: pembaruan data dari sumber dan pembacaan data oleh client. Alur pembaruan juga menghasilkan event untuk consumer. Urutannya adalah sebagai berikut.

\textbf{Pembaruan data dan distribusi event.} Aggregator melakukan polling HTTP dengan credential milik masing-masing sumber. Untuk BMKG, endpoint \texttt{/seismic-events} dan \texttt{/tsunami-warnings} diambil secara concurrent; PVMBG diambil melalui \texttt{/volcanic-reports} pada loop independen. Setelah validasi dan pemetaan, Aggregator menyimpan data terbaru, revisi, serta pesan outbox dalam satu transaksi PostgreSQL.

Outbox merupakan catatan event yang perlu dikirim. Relay membacanya dan menerbitkan envelope melalui protokol NATS. Setelah menerima PubAck dari JetStream, relay menandai pesan telah terpublikasi. Dashboard dan Notifier kemudian meminta pesan dari stream melalui durable pull consumer masing-masing, mengolahnya ke database lokal, lalu mengirim ACK. Mekanisme outbox dan pengiriman ulang dijelaskan pada Bab 8.

\textbf{Pembacaan oleh client.} Client terlebih dahulu login ke Auth melalui HTTP untuk memperoleh token. Pada request data berikutnya, client mengirim Bearer JWT ke Client API. API memverifikasi token secara lokal, memeriksa scope, lalu meminta data ke API internal Aggregator menggunakan key tersendiri. Aggregator membaca Canonical Store, dan Client API mengembalikan field yang diizinkan untuk identitas tersebut. Jalur ini tidak menunggu request baru ke BMKG atau PVMBG.

\section{Kepemilikan Storage dan Container}
Setiap service mengakses data persisten melalui storage yang menjadi tanggung jawabnya. Canonical Store berada di PostgreSQL dan hanya diakses langsung oleh Aggregator. Store ini memuat data terbaru pada \texttt{hazard\_events}, riwayat pada \texttt{hazard\_versions}, status sumber pada \texttt{source\_state}, serta pesan pada \texttt{outbox}. Service lain menggunakan API atau kontrak event untuk memperoleh data.

Auth menyimpan state refresh token dalam SQLite privat. Dashboard dan Notifier juga memiliki SQLite masing-masing untuk mencatat pesan yang sudah diproses dan hasil olahannya. Sementara itu, NATS menyimpan stream pada volume broker. Seluruh storage tersebut menggunakan volume persisten agar penggantian container tidak menghapus state. Sembilan service utama berjalan dalam container terpisah melalui Compose; Third Consumer ditambahkan hanya untuk pengujian melalui profil demo.

\section{Alur Permintaan dan Kegagalan}
Dalam kondisi normal, request client melewati Client API dan Aggregator untuk membaca data yang sudah tersimpan. Polling berjalan di background untuk memperbarui data tersebut. Karena kedua pekerjaan terpisah, delay PVMBG tidak membuat request client menunggu respons PVMBG dan tidak menghalangi polling BMKG.

Saat PVMBG mengalami outage, Aggregator tetap menyediakan record terakhir yang berhasil disimpan, dengan penanda \textit{stale} untuk menunjukkan bahwa data belum diperbarui. Jika belum ada record yang dapat dilayani, request khusus sumber tersebut memperoleh status unavailable. Ketika sumber pulih, polling berikutnya memperbarui data dan status freshness tanpa perlu restart. Perilaku serta batas ketersediaannya diuji pada Bab 5.

Pada jalur event, kegagalan broker membuat pesan tetap menunggu di outbox untuk dicoba kembali. Jika hanya consumer yang berhenti, broker tetap menyimpan event dan consumer lain tetap dapat membacanya. Consumer yang pulih melanjutkan pembacaan menggunakan posisi durable selama pesan yang dibutuhkan masih berada dalam retention. Pemisahan ini tidak menyediakan failover untuk Aggregator, PostgreSQL, atau broker yang masing-masing masih menggunakan satu instance.
