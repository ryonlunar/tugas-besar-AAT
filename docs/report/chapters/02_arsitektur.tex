\section{Alur data dan batas service}
Alur dimulai ketika Aggregator melakukan polling ke BMKG dan PVMBG. Masing-masing sumber memiliki loop sendiri agar sumber yang lambat tidak menunda pengambilan data dari sumber lain. Setelah respons dipetakan menjadi \texttt{HazardEvent}, Aggregator menyimpan data terbaru, snapshot revisi, dan pesan outbox dalam satu transaksi PostgreSQL. Outbox merupakan daftar pesan yang sudah menjadi bagian dari data tersimpan, tetapi masih perlu dikirim ke broker. Relay membacanya dan melakukan publish ke JetStream, termasuk mencoba kembali jika publish gagal.

Ada dua jalur untuk menggunakan data tersebut. Pada jalur baca, client memperoleh JWT dari Auth, lalu mengirimkannya ke Client-Facing API. API memeriksa signature dan scope secara lokal sebelum membaca data melalui API internal Aggregator. Pada jalur event, Dashboard dan Notifier mengambil pesan dari JetStream, mengolahnya, kemudian menyimpan hasil pada database masing-masing. Notifier hanya mencatat alert lokal sebagai simulasi notifikasi pada M1.

\section{Alasan pembagian service}
Kontrak BNPB pada spesifikasi M1 mencantumkan Aggregator, Client-Facing API, Auth/Token Service, dan sedikitnya dua Event Consumer. Ketentuan implementasi juga mewajibkan container terpisah serta satu pemilik untuk setiap storage \cite{m1}. Pembagian tanggung jawab berikut menerapkan ketentuan tersebut dan membatasi bagian yang harus berubah bersama.

Aggregator menangani polling, pemetaan, dan transaksi Canonical Store, sedangkan Client API memeriksa izin client dan menyajikan data. Dengan pemisahan ini, perubahan login atau antarmuka client dapat dilakukan tanpa membangun ulang ingest. Client API tetap membaca melalui HTTP Aggregator sesuai aturan ownership. REST/JSON dipilih karena bentuk data yang sama dapat digunakan pada jalur baca dan mudah diperiksa dengan curl. Konsekuensinya, pembacaan membutuhkan satu panggilan jaringan tambahan dan tetap bergantung pada Aggregator.

Auth menangani pemeriksaan credential client, penerbitan token, dan sesi refresh. Client API memverifikasi token serta menegakkan hak akses, sehingga ia cukup memiliki public key; private key tetap berada di Auth. Menggabungkan keduanya akan mengurangi jumlah proses, tetapi mengikat deploy login dan pembacaan data dalam satu unit serta menempatkan key penandatanganan pada proses yang melayani data. Dengan verifikasi JWT lokal, gangguan Auth tidak menghentikan penggunaan access token yang masih valid. Login dan refresh tetap memerlukan Auth.

Polling BMKG dan PVMBG tetap berada dalam satu Aggregator karena keduanya membentuk HazardEvent dan menggunakan Canonical Store yang sama. Loop serta pool koneksi dipisahkan untuk mengisolasi pekerjaan sumber tanpa menambah service ingest per instansi. Relay outbox juga berjalan sebagai worker di Aggregator, sehingga pembacaan outbox tetap dilakukan oleh pemilik storage. Batas ini mengurangi jumlah antarmuka yang harus dikelola, tetapi polling, pemetaan, dan relay masih ikut berhenti jika container Aggregator mati.

Dashboard dan Notifier dipisahkan karena hasil olahannya berbeda: Dashboard menyimpan proyeksi data terbaru, sedangkan Notifier mencatat alert. Satu proses dengan dua handler dapat menjalankan kedua fungsi, tetapi penghentian proses tersebut akan menghentikan keduanya. Container dan durable yang terpisah memungkinkan setiap consumer berhenti, pulih, atau berubah tanpa mengganti consumer lain.

\section{Jaringan dan kepemilikan storage}
Canonical Store hanya dapat diakses langsung oleh Aggregator; Client API mengaksesnya melalui HTTP, sedangkan consumer menerima event melalui broker. PostgreSQL dan NATS tidak membuka port ke host. Auth dan setiap consumer juga memiliki volume SQLite sendiri, sehingga mereka tidak saling membaca database lokal.

Empat jaringan Compose dipilih untuk membatasi hubungan sesuai jalur komunikasinya. Dibanding satu jaringan untuk seluruh container, konfigurasi ini mengurangi jalur akses yang tidak diperlukan, dengan konsekuensi pengaturan jaringan menjadi lebih banyak. Pembatasan tersebut melengkapi autentikasi pada setiap antarmuka.

Antarservice berkomunikasi melalui antarmuka jaringan. Paket bersama dipakai untuk kontrak pesan dan utilitas teknis; aturan pemetaan, otorisasi, serta pengolahan event tetap berada pada service yang bertanggung jawab.

Demo console disediakan sebagai alat operator untuk menjalankan command HTTP dan Docker serta melihat output terminal. Alat ini berbeda dari Dashboard Consumer yang mengolah event. Seluruh service dapat dijalankan dan diuji melalui CLI tanpa membuka demo console.
