\chapter{KESIMPULAN}
Implementasi M1 menghubungkan mock BMKG dan PVMBG melalui Aggregator, lalu menyediakan hasilnya kepada client dan consumer dengan kontrak yang terpisah. Pada profil data awal yang diuji, pemetaan menghasilkan HazardEvent yang valid dan menerima tambahan atribut PVMBG tanpa restart atau migrasi tabel. Client API juga membatasi field sesuai identitas, termasuk menolak permintaan data raw dari Media.

Pemisahan jalur polling dan baca menjaga layanan ketika PVMBG mengalami gangguan. Saat outage, API tetap mengembalikan data terakhir dengan penanda stale, sementara BMKG tetap diperbarui. Pada load test dengan 60 worker dan delay PVMBG 3 detik, p95 BMKG mencapai 124,52 ms, throughput 980,26 respons sukses per detik, dan error selain 429 sebesar 0,034\%. Sampel TCP menunjukkan sedikitnya 50 koneksi selama 89,00 detik. Hasil tersebut memenuhi ambang P2 pada profil beban yang diuji.

Pada jalur event, Dashboard dapat dihentikan atau dibangun ulang ketika producer dan Notifier tetap berjalan. Setelah pulih, Dashboard melanjutkan pembacaan event yang tersimpan di broker. Third Consumer juga berhasil ditambahkan tanpa perubahan producer. Hasil ini menunjukkan bahwa container terpisah, durable independen, dan storage privat mendukung operasi serta pemulihan per consumer.

Batas utama yang masih perlu ditangani adalah pertumbuhan data dan deployment satu instance. Sebelum meningkatkan volume, sistem perlu mengurangi biaya full snapshot, menguji ulang kapasitas, serta menetapkan pembersihan history, inbox, dan outbox. Jika jumlah instance ditambah pada milestone berikutnya, polling, relay, dan state service juga membutuhkan koordinasi. Di sisi keamanan, sinkronisasi waktu, TLS, pemisahan credential broker, serta rotasi key perlu disiapkan untuk penggunaan di luar demo lokal.
