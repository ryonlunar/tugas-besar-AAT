\begin{center}\large\bfseries SERVICE-TO-SERVICE AUTHENTICATION DAN TRUST\end{center}
Bukti runtime pada bab ini mencakup trial 5 Oktober dan tangkapan command 7 Oktober 2026, yang merupakan sesi pengujian berbeda [10].


\section{Credential dan hak akses}
Setiap sumber memiliki credential sendiri: BMKG menerima API key melalui header \texttt{X-BMKG-Key}, sedangkan PVMBG menerima Bearer token sumber. API internal Aggregator memakai key lain. Pemisahan ini membuat kebocoran satu credential tidak otomatis memberikan akses ke seluruh antarmuka, dan credential sumber tidak dapat dipakai sebagai identitas client.

Untuk akses client, Auth membedakan identitas \texttt{media}, \texttt{field-team}, dan \texttt{bnpb-internal}. Media hanya memiliki scope ringkasan, yang berisi tepat tujuh field: \texttt{hazard\_id}, \texttt{source}, \texttt{hazard\_type}, \texttt{severity}, \texttt{area\_name}, \texttt{occurred\_at}, dan \texttt{ingested\_at}. Scope lengkap menambahkan \texttt{source\_ref\_id}, koordinat, dan \texttt{attributes}.

Pembatasan dilakukan oleh Client API sebelum data diminta dari Aggregator. Jadi, Media tidak dapat memperoleh data raw hanya dengan mengubah query menjadi \texttt{view=full} atau meminta field tambahan secara eksplisit; kedua request tersebut ditolak dengan 403. Aturan akses berada di server, sehingga tidak bergantung pada tampilan yang dipakai client.

Auth menerbitkan JWT [11] yang ditandatangani menggunakan RS256 dan private key. API hanya memerlukan public key untuk memeriksa signature, issuer, audience, expiry, serta scope. Verifikasi dilakukan secara lokal, sehingga token yang masih valid tetap dapat digunakan saat Auth berhenti sementara; perilaku ini diperiksa pada trial integrasi [10]. Jika API memakai shared signing secret, material untuk memverifikasi juga dapat digunakan untuk membuat token. Sementara itu, introspection ke Auth pada setiap request memudahkan pemeriksaan status token secara terpusat, tetapi menambahkan dependency pada jalur baca. Untuk milestone 1, verifikasi lokal dipilih bersama TTL yang singkat.

\section{Expiry dan refresh}
Default masa berlaku access token adalah 60 detik dan dapat dikonfigurasi melalui \texttt{ACCESS\_TOKEN\_TTL}. Profil pengujian milestone 1 dalam laporan ini tetap menggunakan \texttt{60s}; nilainya tidak diperpanjang untuk meloloskan load test. Agar client dapat melanjutkan sesi tanpa login ulang, Auth juga memberikan refresh token berupa nilai acak. Hanya hash token tersebut yang disimpan di SQLite. Setiap refresh menghasilkan token baru dan menandai token refresh sebelumnya sudah digunakan. Jika token lama dipakai kembali, keluarga sesi itu dibatalkan untuk mencegah kelanjutan refresh dari token yang digunakan ulang.

Batas umur keluarga sesi refresh memiliki default 24 jam dan dapat dikonfigurasi melalui \texttt{REFRESH\_TOKEN\_TTL}; profil pengujian memakai \texttt{24h}. Kedua TTL harus bernilai positif. Expiry keluarga sesi tetap dihitung dari pembentukan sesi dengan TTL yang berlaku saat itu, sehingga rotasi tidak memperpanjang sesi tanpa batas. Database Auth berada pada volume privat agar sesi refresh tidak hilang ketika container dijalankan ulang.

Rotasi refresh token tidak langsung mencabut access JWT yang belum expired. API tidak memiliki daftar revocation untuk access token; token tersebut masih dapat digunakan sampai \texttt{exp}. Pengujian menunggu expiry alami sebelum memeriksa penolakan token lama dengan status 401.

\section{Batasan keamanan dan waktu}
Expiry JWT mengikuti wall clock. Pada implementasi ini, \texttt{iat} yang tampak berada di masa depan ketika clock mundur tidak dijadikan alasan tunggal untuk menolak token. API tetap memeriksa signature, issuer, audience, scope, expiry, serta \texttt{nbf} jika claim tersebut ada. Pada profil pengujian, selisih \texttt{exp-iat} adalah 60 detik sesuai konfigurasi \texttt{ACCESS\_TOKEN\_TTL}, tetapi pergeseran waktu host dapat mengubah kapan batas itu tercapai: clock mundur dapat memperpanjang masa berlaku yang dirasakan, sedangkan clock maju dapat membuat token lebih cepat expired. Sinkronisasi waktu diperlukan agar TTL sesuai dengan waktu nyata.

Di luar masalah waktu, komunikasi HTTP internal belum memakai TLS dan domain event masih menggunakan token NATS bersama. Sistem juga belum menyediakan rotasi key RSA maupun pencabutan access JWT secara langsung. Sebelum digunakan pada jaringan yang tidak dipercaya, perlindungan koneksi dan pemisahan credential broker perlu ditambahkan.
