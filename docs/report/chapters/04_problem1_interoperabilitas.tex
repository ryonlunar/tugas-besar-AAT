\chapter{PROBLEM 1}
\begin{center}\large\bfseries ARSITEKTUR DAN INTEROPERABILITAS DATA\end{center}

\section{Masalah dan Kriteria}
BMKG memisahkan gempa dan warning tsunami, sedangkan PVMBG memakai laporan gunung api tanpa koordinat langsung. Aggregator perlu menghasilkan model kanonik yang konsisten dan tetap memproses laporan ketika PVMBG menambah \texttt{confidence\_level}, tanpa restart atau perubahan tabel [1]. Normalisasi tidak boleh membuang field tambahan atau menyamarkan record invalid sebagai data valid.

\section{Solusi yang Diimplementasikan}
Mapper membaca field sebagai \texttt{json.RawMessage}, memvalidasi field wajib, lalu mempertahankan nilai dinamis menggunakan \texttt{json.Number}. Output \texttt{HazardEvent} memiliki sebelas field: ID hazard, source, source reference, tipe, severity, area, latitude, longitude, waktu kejadian, waktu ingest, dan attributes. Metadata delivery ditempatkan pada envelope, bukan ditambahkan ke entity.

Untuk BMKG, \texttt{event\_id} menjadi \texttt{source\_ref\_id}, region dan koordinat episentrum dipertahankan, dan tipe menjadi \texttt{SEISMIC}. Warning divalidasi secara mandiri sebelum dikelompokkan berdasarkan \texttt{related\_event\_id}. Warning rusak menandai siklus degraded tanpa menggugurkan gempa valid. Warning hanya terpasang pada gempa dengan \texttt{potential\_tsunami=true}; jika ada beberapa warning, severity tertinggi dipilih dan seluruh warning valid disimpan terurut dalam attributes.

Tanpa warning, magnitude di bawah 5,0 menjadi NORMAL; 5,0 hingga kurang dari 6,5 menjadi WASPADA; dan mulai 6,5 menjadi SIAGA. Untuk PVMBG, \texttt{report\_id} menjadi source reference, \texttt{reported\_at} menjadi waktu kejadian, dan enum alert dipetakan secara eksplisit ke enum kanonik. Area dan koordinat diambil dari referensi sintetis Tamriel berdasarkan \texttt{volcano\_id}; ID tak dikenal ditolak, bukan diberi koordinat nol.

Identitas permanen mengikuti pasangan \texttt{(source, source\_ref\_id)}. Data pertama memperoleh UUIDv4; perubahan isi mempertahankan UUID dan menghasilkan revisi baru. Full snapshot memungkinkan warning yang baru tersedia memengaruhi hazard lama pada poll berikutnya. Poll identik hanya memajukan freshness sumber dan tidak membuat event/outbox duplikat.

\section{Evolusi Skema dan Trade-off}
Field tambahan yang tidak mempunyai padanan kanonik disimpan dalam \texttt{attributes}; collision dengan atribut hasil turunan dipertahankan dalam \texttt{source\_extras}. Penambahan \texttt{confidence\_level} tidak memerlukan migrasi tabel. Field wajib hilang, perubahan tipe, enum invalid, duplicate key, dan JSON invalid ditolak; siklus degraded tidak menaikkan waktu sukses terakhir.

Decode langsung ke struct lebih sederhana, tetapi dapat mengabaikan field tambahan. RawMessage dan validasi eksplisit dipilih agar evolusi aditif tidak menghilangkan data [4]. Full snapshot lebih mudah menjaga korelasi dan update record lama daripada cursor incremental, dengan trade-off biaya baca yang bertambah. Fleksibilitas JSONB tidak menggantikan validasi domain [5].

\section{Batasan yang Disadari}
Field baru disimpan tanpa otomatis menjadi field ringkasan atau mengubah severity. Rename atau penghapusan field wajib membutuhkan perubahan kontrak. Fixture Tamriel hanya untuk simulasi. Jalur warning terlambat tersedia, tetapi pengujian khusus dari poller sampai revisi PostgreSQL belum dijalankan sebagai satu skenario acceptance terpisah.

\section{Bukti Penyelesaian}
Tes mapper lulus untuk batas magnitude, prioritas dan korelasi warning, preservasi field dinamis, bentuk PVMBG v1/v2, serta penolakan enum/ID/duplicate key invalid. Tes poller lulus untuk warning rusak yang terkait maupun tidak terkait: gempa valid tetap diteruskan dan siklus ditandai degraded.

Smoke HTTP terbaru membuktikan seed 20 record, penolakan akses tanpa credential dengan 401, PVMBG v1 tanpa dan v2 dengan \texttt{confidence\_level}, ID laporan tetap sama setelah toggle, serta respons 503 saat outage. Tes PostgreSQL membuktikan ID hazard tetap, revisi dan outbox tidak bertambah pada payload identik, dan snapshot riwayat sebelum/sesudah field baru tetap dapat dibaca. Ini merupakan bukti komponen pada commit \texttt{19beead}, bukan klaim bahwa seluruh acceptance P1 sudah diuji end-to-end.

\subsection{Bukti Integrasi}
Evidence berikut berasal dari trial dan tangkapan command yang disertakan dalam repository [10]. Trial 5 Oktober memakai commit \texttt{071b32d}; command 7 Oktober menyediakan contoh pemetaan dan audit schema tambahan.

Pada contoh BMKG 7 Oktober, magnitude 4,2 tanpa potensi tsunami menjadi severity NORMAL; region dan koordinat dipertahankan pada field kanonik. Contoh PVMBG v1 mempunyai alert Normal, menjadi VOLCANIC/NORMAL, dan ID Red Mountain dipetakan ke koordinat sintetis $(-7,108)$. Source reference pada masing-masing hasil tetap menunjuk record sumber yang dipilih. Log validasi draft mencatat delapan record HazardEvent valid: empat dari trial 5 Oktober dan empat dari command 7 Oktober. Pernyataan ini mengenai record yang diperiksa, bukan seluruh kemungkinan input.

Pengujian schema memakai \texttt{POST /admin/schema-version} dengan versi 2, lalu membaca \texttt{history-audit --revisions 1,2} melalui binary Aggregator. Revisi pertama tidak memiliki confidence; revisi kedua memiliki nilai 0,58. Keduanya mempertahankan ID hazard dan source reference yang sama. Daftar migrasi tetap dua migrasi awal; confidence disimpan sebagai tambahan atribut JSONB.

\subsection{Temuan pada Volume Lebih Besar}
Catatan review historis melaporkan toggle v2 pada stack yang telah menyimpan sekitar 1.000 record sumber. Respons mock sudah berubah, tetapi revisi baru untuk record yang diperiksa belum tersimpan; log Aggregator berulang kali menunjukkan \texttt{POLL\_FAILED}. Mengembalikan schema ke v1 memulihkan polling/publication. Catatan ini bukan pengukuran load baru dan tidak dibantah oleh keberhasilan trial dengan seed awal [10].

Deadline write 2 detik diduga berpengaruh ketika satu snapshot memperbarui banyak record, tetapi penyebabnya belum dipastikan. Tidak ada perubahan kode atau timeout dalam catatan tersebut. Sebelum menyatakan dukungan schema pada volume yang terus tumbuh, perlu diagnosis serta pengukuran ulang; pagination, change feed, atau batch lebih kecil adalah opsi evaluasi, bukan fitur yang sudah diterapkan.
