\chapter{DESKRIPSI UMUM SISTEM}

\section{Latar Belakang}
Sistem ini dibangun untuk memenuhi tugas besar IF4031 Arsitektur Aplikasi Terdistribusi, yang mengangkat kebutuhan pertukaran data kebencanaan antarinstansi. BMKG menyediakan informasi gempa dan peringatan tsunami, sedangkan PVMBG menyediakan laporan aktivitas gunung api. BNPB berperan sebagai simpul koordinasi yang menyatukan informasi tersebut untuk Media, Tim Lapangan, dan kebutuhan internal. Karena setiap instansi memiliki format data dan mekanisme akses sendiri, pertukaran data ini membutuhkan perantara yang dapat menangani perbedaan tersebut [1,2].

Pada Milestone 1 (M1), kebutuhan tersebut diwujudkan melalui sistem agregasi dan distribusi data. Sistem mengambil data dari mock BMKG dan PVMBG, mengubahnya ke format bersama (canonical), lalu menyediakannya melalui API dan distribusi event. Selain fungsi integrasi, implementasi harus tetap dapat melayani client ketika salah satu sumber lambat atau tidak tersedia, serta membatasi data sesuai hak akses client.

\section{Tujuan}
Lima problem pada M1 menjadi dasar perancangan dan pengujian sistem:
\begin{enumerate}
  \item Menyatukan data seismik dan vulkanik, termasuk menerima tambahan field sumber tanpa restart.
  \item Menjaga layanan baca tetap responsif ketika PVMBG lambat atau mengalami outage.
  \item Memisahkan credential antarinstansi dan menegakkan hak akses setiap client.
  \item Memisahkan komponen agar satu service dapat diganti tanpa menjalankan ulang seluruh sistem, sekaligus menjaga kepemilikan storage.
  \item Mendistribusikan event ke beberapa consumer yang dapat berhenti dan pulih secara independen.
\end{enumerate}
Rancangan, pertimbangan, batasan, dan bukti untuk setiap tujuan dibahas pada Bab 4--8.

\section{Ruang Lingkup}
Implementasi M1 menggunakan mock BMKG dan PVMBG sebagai sumber data, dengan BNPB sebagai node koordinasi. Data yang ditangani terbatas pada bahaya seismik dan vulkanik. Kedua mock menyediakan data sintetis dan kontrol untuk menguji perubahan schema, delay, serta outage.

Ketiga client hanya membaca data. Pelaporan dari lapangan, kebakaran hutan, serta jenis bahaya lain belum termasuk cakupan M1 [1,2]. Dua consumer memperagakan pembaruan dashboard dan notifikasi, dengan notifikasi dicatat di storage lokal sebagai simulasi.

\section{Istilah dan Data Kanonik}
Rincian pemetaan dibahas pada Bab 4. Istilah \textit{kanonik} merujuk pada format bersama untuk mewakili kejadian dari kedua sumber. Format ini bernama \texttt{HazardEvent}, dengan identitas, jenis bahaya, severity, lokasi, waktu, dan atribut sumber.

BMKG menyediakan \texttt{SeismicEvent} dan \texttt{TsunamiWarning}, yang dihubungkan melalui \texttt{related\_event\_id}. PVMBG menyediakan \texttt{VolcanicReport}. Aggregator memetakan kedua sumber ke HazardEvent, dengan rincian khusus sumber dan field baru, seperti \texttt{confidence\_level}, disimpan dalam \texttt{attributes}.
