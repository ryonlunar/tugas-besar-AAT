\section{Container dan ownership}
Stack utama terdiri dari tujuh container aplikasi serta dua container infrastruktur, yaitu PostgreSQL dan NATS. Setiap aplikasi memiliki Dockerfile sendiri, sementara kedua komponen infrastruktur memakai image resmi. Third Consumer hanya dijalankan melalui profile demo. Compose membantu mengatur jaringan dan urutan startup, tetapi satu aplikasi tetap dapat dibangun dan diganti dengan \texttt{--no-deps} tanpa menjalankan ulang seluruh stack.

Canonical Store menjadi tanggung jawab Aggregator. Hanya Aggregator dan PostgreSQL yang terhubung ke \texttt{store-net}, dan PostgreSQL tidak membuka host port. Karena itu, Client API membaca data melalui HTTP Aggregator. Consumer memperoleh data melalui NATS, lalu menyimpan hasil olahan dalam database lokalnya sendiri. Perintah audit juga dijalankan melalui binary Aggregator agar inspeksi data tetap dilakukan oleh service pemiliknya.

Pembagian tersebut menghindari ketergantungan consumer pada schema tabel internal Aggregator. Sebagai konsekuensinya, tampilan consumer diperbarui secara eventual: perubahan canonical harus melewati outbox dan broker sebelum diterapkan pada database consumer. Shared database antarservice dapat mengurangi jumlah antarmuka HTTP, tetapi perubahan tabel akan mengikat beberapa aplikasi sekaligus dan tidak memenuhi ownership storage yang diminta spesifikasi.

\section{Detail Implementasi Canonical Store}
Aggregator menggunakan PostgreSQL dengan empat kelompok tabel. \texttt{hazard\_events} menyimpan state terbaru dan unique key sumber/reference; \texttt{hazard\_versions} menyimpan snapshot append-only per revisi; \texttt{source\_state} menyimpan percobaan, sukses, kegagalan, dan freshness; \texttt{outbox} menyimpan envelope immutable yang belum atau sudah dipublikasikan. Field kanonik memiliki tipe dan constraint, sedangkan atribut sumber memakai JSONB [5].

Perubahan latest hazard, penambahan versi, dan outbox ditulis dalam satu transaksi. Jika isi identik secara semantik, termasuk angka JSON yang ekuivalen, revisi tidak ditambah. Kapasitas pending outbox diperiksa secara atomik; snapshot yang melampaui batas tidak di-commit. Pool baca dipisahkan dari writer BMKG, writer PVMBG, dan relay sehingga request baca tidak menunggu delay sumber.

Migrasi versioned dijalankan Aggregator saat startup dengan advisory lock dan checksum. Schema v2 PVMBG hanya menambah key JSONB, bukan migrasi baru. CLI audit pada binary Aggregator membaca versi terpilih melalui adapter Store lokal; tidak tersedia endpoint history publik atau akses database untuk consumer.

\section{Struktur Storage dan Alternatif}
Field canonical yang stabil disimpan dalam kolom bertipe dengan constraint, sedangkan \texttt{attributes} memakai JSONB untuk menampung atribut yang dapat bertambah. Data terbaru berada di \texttt{hazard\_events} dan setiap revisinya dicatat dalam \texttt{hazard\_versions}. Dua tabel lain melengkapi alur ingest: \texttt{source\_state} menyimpan kondisi polling, sementara \texttt{outbox} mencatat pesan yang perlu dipublikasikan.

Dengan struktur ini, tambahan \texttt{confidence\_level} masuk ke dokumen atribut tanpa \texttt{ALTER TABLE}. Pilihan tersebut dibandingkan dengan dua alternatif pada tabel berikut.

\section{Verifikasi Komponen Storage}
Verifikasi native pada commit \texttt{19beead}, dengan PostgreSQL 18.6 dan NATS 2.10.24, lulus untuk UUID stabil, revisi/history, idempotensi, kapasitas outbox, presisi angka, dan round-trip JSONB ke JetStream. Tes normal dan race, build, vet, serta module verify lulus. Database disposable berakhiran \texttt{\_test} memakai reset opt-in, tanpa mengakses database aplikasi. Bukti ini melengkapi sesi Compose, tetapi bukan pengulangan deployment PostgreSQL 16 atau restart seluruh aplikasi.
\section{Batasan}
Pemisahan aplikasi/jaringan tidak membatasi administrator Docker. Rebuild satu consumer tidak membuktikan ketersediaan API ketika Aggregator atau PostgreSQL mati. History, inbox, dan outbox terpublikasi belum memiliki pembersihan jangka panjang; retention lokal dan batch snapshot besar pada P1 masih perlu ditangani sebelum peningkatan volume.
