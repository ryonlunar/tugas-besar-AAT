\chapter{Problem 4: Arsitektur Microservice \& Flexible Storage}
\section{Container dan ownership}
Stack utama terdiri dari tujuh container aplikasi serta dua container infrastruktur, yaitu PostgreSQL dan NATS. Setiap aplikasi memiliki Dockerfile sendiri, sementara kedua komponen infrastruktur memakai image resmi. Third Consumer hanya dijalankan melalui profile demo. Compose membantu mengatur jaringan dan urutan startup, tetapi satu aplikasi tetap dapat dibangun dan diganti dengan \texttt{--no-deps} tanpa menjalankan ulang seluruh stack.

Canonical Store menjadi tanggung jawab Aggregator. Hanya Aggregator dan PostgreSQL yang terhubung ke \texttt{store-net}, dan PostgreSQL tidak membuka host port. Karena itu, Client API membaca data melalui HTTP Aggregator. Consumer memperoleh data melalui NATS, lalu menyimpan hasil olahan dalam database lokalnya sendiri. Perintah audit juga dijalankan melalui binary Aggregator agar inspeksi data tetap dilakukan oleh service pemiliknya.

Pembagian tersebut menghindari ketergantungan consumer pada schema tabel internal Aggregator. Sebagai konsekuensinya, tampilan consumer diperbarui secara eventual: perubahan canonical harus melewati outbox dan broker sebelum diterapkan pada database consumer. Shared database antarservice dapat mengurangi jumlah antarmuka HTTP, tetapi perubahan tabel akan mengikat beberapa aplikasi sekaligus dan tidak memenuhi ownership storage yang diminta spesifikasi.

\section{Struktur storage dan alternatif}

Data terbaru berada di \texttt{hazard\_events} dan setiap revisinya dicatat dalam \texttt{hazard\_versions}. Dua tabel lain melengkapi alur ingest: \texttt{source\_state} menyimpan kondisi polling, sementara \texttt{outbox} mencatat pesan yang perlu dipublikasikan.

\section{Batasan}
Batas ownership diterapkan pada aplikasi dan jaringan Compose. Administrator Docker tetap dapat memasuki container atau memasang volume, sehingga pemisahan ini tidak membatasi administrator host. Pengujian rebuild juga hanya membuktikan isolasi satu consumer; ketersediaan API saat Aggregator atau PostgreSQL mati belum dibuktikan oleh pengujian tersebut.

Selain itu, history, inbox, dan outbox yang telah dipublikasikan belum memiliki kebijakan pembersihan jangka panjang. Kebutuhan ruang akan terus meningkat jika data dibiarkan bertambah. Masalah batch snapshot besar yang dibahas pada P1 serta kebijakan retention lokal perlu diselesaikan sebelum sistem digunakan untuk volume yang lebih tinggi.
